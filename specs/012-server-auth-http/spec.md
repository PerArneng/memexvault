# 012 server-auth-http

## Goal
A running server hosting several isolated vaults, where each human or agent token has per-vault read, propose or admin
scope, and every write records who made it.

## Background
**Depends on:** 032, 011. Design: `docs/architecture.md`, sections Decisions, Crates.

## Approach
- `Engine` facade with one method per use case. `memex-http` only parses, calls and formats. DTOs live in `memex-api`.
- A server registry in the `memex_server` schema, separate from any vault: vaults, principals (human or agent), token hashes and scopes.
- Tokens are random, shown once and stored hashed, with revocation and expiry through `Clock`.
- Authorization is a pure function of principal, vault and operation.
- API: vault create and list, token create, list and revoke, whoami, health, version.
- Binds to localhost by default. Body size limits, request ids, a consistent error format and an OpenAPI document.
- A first-run bootstrap creates an admin token once.
- API conventions from `docs/architecture.md`, with a shared list helper. Vault get, rename and delete, and a server-admin flag on principals that controls creating vaults. Principal list, create and disable. Tokens carry expiry, scopes and last-used, and token lists show them.

## Verification
1. A table-driven test of all scopes × all operations × own and other vault, with no gaps. Every denied case returns the
   right status and leaves no state change.
2. A token for vault A can't detect that vault B exists: same response as for a missing vault.
3. Every write event in an integration test has the correct actor, and no write path exists without one.
4. Bad cases: revoked, expired and malformed tokens; oversized bodies; the token doesn't appear in logs (tested by
   capturing logs).
5. `cargo tree -p memex-core` still lists no axum or tokio.
6. Every list route in the OpenAPI document has a cursor, limit and stated sort, checked by a test that reads the document.

## Out of scope
TLS (use a reverse proxy if needed), SSO or OAuth, and per-object ACLs. The console is covered by specs 037, 040 and 048.

## Result
Built the running server. `Server<E: ServerEdges>` in `memex-core` is the facade above vault level, holding each vault's writer lease. `authorize` is a pure function. The `Registry` trait has `MemRegistry` and a Postgres implementation in the `memex_server` schema, with a shared contract suite. `memex-http` is axum with thin handlers that call the core on a blocking thread, DTOs are in `memex-api`, and the OpenAPI document is generated by `utoipa` at `/api/v1/openapi.json`. The binary has `migrate`, `bootstrap <name>` and `serve`.

Routes: health, version, whoami, vaults (create, list, get, rename, delete), principals (create, list, disable), tokens (create, list, revoke), all under `/api/v1`.

**Verification.** `cargo test -p memex-core -p memex-api -p memex-http`: all pass, with no database.
1. A table-driven test runs 16 route cases against tokens with read, propose, admin and no scope, 64 combinations in total, through the real router. Each checks the status, and every denial leaves the registry unchanged by fingerprint and returns the one error format. A pure test covers scope against operation for own and other vault, and another that a server admin may do everything.
2. A token for vault A gets byte-identical responses, apart from the request id, for vault B and for a vault that doesn't exist, on GET, PATCH and DELETE. Its vault list shows only A.
3. Every write has an actor. `apply_as` takes the actor from the token, so a payload naming another actor changes nothing, and registry writes store an audit row in the same transaction. There's no way to write without one.
4. Bad cases: wrong, garbage, oversized, revoked, expired and disabled-owner tokens and a missing token all give the same 401 body. A non-Bearer scheme is refused. A 1 MiB-plus body gets 413 and malformed JSON 400, both in the one format. A test binary with a captured global log shows no token even when a token is sent as a query string, and a backend's detail goes to the log, not to the caller.
5. `cargo tree -p memex-core` lists no axum or tokio.
6. A test reads the OpenAPI document: each of the 3 list routes has `cursor`, `limit` and `sort`, and every served route is documented.

**End to end on Postgres**, with the release binary: `migrate`, `bootstrap` printing a 68-character token once, a second `bootstrap` refused, `serve`, `whoami`, creating a vault that made a real schema with `events`, `sources`, `pages` and `edges` tables, paging, 401 with no token, and audit rows present. The token wasn't in the server's log. Binary 5.0 MB, linking system libraries only. `pg_registry_contract` passes.

**Found by reviewing my own code:** a token carries its owner's rights, so a vault admin could have minted a token owned by a server admin. That's now refused, with a test. Also refused: a server admin disabling themselves, which could leave no admin.

**Decisions.**
- `SystemSeed` now reads the OS random source through `getrandom`, because tokens need real randomness. The earlier standard-library hasher keys weren't suitable. A token is `mvx_` and 256 random bits, stored as SHA-256, which is fine for high-entropy secrets.
- Ids put time first, like UUIDv7, so id order is creation order and `sort=created` is real. They're hex, so they're safe as folder and schema names.
- `last_used` is written at most once a minute, so reads don't all become writes.
- Vault delete removes the registry row first, then the schema, then the blobs. A failure part way leaves unreachable data for spec 030's sweep, never a visible vault with missing data.
- `purge_incomplete` runs when a lease is taken, as spec 011 required.

**Not covered yet:** rate limiting of failed logins belongs to spec 037, and an admin UI to spec 048.
